# Agent 课程笔记

> 规划 Planner 时边讨论边讲的 Agent 概念，用 Meri 自己的代码和试验举例。每次讨论加一课。
> 规划本身见 [README.md](README.md)。

## 第 1 课：Agent 到底是什么

用 1.0300 的试验举例，问题是"丽江的玉龙雪山值得去吗？"：

```text
① 程序把三样东西发给模型：指令（你是谁、规则）、问题、工具清单（名字、用途、参数格式）
② 模型回答的不是文字，而是："我要调用 resolvePlace，参数 {name: 玉龙雪山}"
③ 程序（不是模型）真的去查高德，拿到结果
④ 程序把结果加进对话，再发给模型
⑤ 模型看了结果，决定：再调一个工具，或者直接回答
⑥ 重复 ②–⑤，直到模型直接回答，或者碰到步数上限
```

要点：
- **模型自己不执行任何东西**，只是提出"我想调用什么"，执行的永远是我们的代码。所以安全控制都在代码这边：给它哪些工具、参数怎么校验、结果给它看多少。
- **Agent 和普通模型调用的区别在第 ⑤ 步**：下一步做什么，由模型根据上一步的结果决定。Meri 的聊天是固定流程：模型理解一次，代码按规则执行，不循环。
- **每转一圈都要把之前所有内容再发一遍**，所以循环越多越慢、越贵。这就是为什么要设预算上限，也是为什么要做评估。
- **并行工具调用**：试验第 2 题，模型在同一步里同时调了搜索和查地点，因为它判断两件事互不依赖。

## 第 2 课：生成者 + 验证者

```text
Agent（生成者）：查资料，提出一天的安排
        ↓
验证者（代码规则）：路上总时长超过 6 小时？景点 17:00 关门却安排 16:30 到？
                    徒步 5 小时但 18:30 日落？
        ↓
有问题 → 把问题原样告诉 Agent，让它修改（反思循环，也要设次数上限）
没问题 → 保存
```

验证者为什么用**代码规则**，不用另一个模型判断？
- 规则是确定的：同样的输入永远同样的结论，能写单元测试。
- 模型判断会有偏差：试验里模型说"两个地点都已核实"，其实有一个没核实成功。
- 用模型打分（**LLM-as-judge**）适合"这个安排有没有意思"这类没有标准答案的问题，以后做评估时会用到。

一句话：**事实类检查用规则，主观质量用模型打分。**

## 第 3 课：MCP 是什么

- **没有 MCP 时**：每接一个服务都要自己写一个工具，读它的文档、写请求、解析结果，就像现在的高德和 Bocha。
- **MCP（Model Context Protocol）** 是一个标准协议：服务方按统一格式发布自己的工具（名字、说明、参数格式），支持 MCP 的程序连上就能直接用。
- **Mastra 有 MCP 客户端**：连上途牛、RollingGo 这类 MCP 服务器，它们的工具可以直接给 Agent 用。
- **代价**：工具说明和返回格式都是对方定的，对方一改，我们 Agent 的行为也可能跟着变。所以中间要加一层：只挑白名单里的工具（比如不给下单工具），返回结果再缩减和校验一遍。

## 第 4 课：Agent 的记忆

三种记忆：
- **短期记忆**：这次对话的上下文，每一轮模型都能看到，但有长度上限。
- **长期记忆**：跨对话保留的东西，比如用户画像、说过的话。
- **压缩**：上下文太长时，把旧内容缩短。

压缩有两种做法：
- **压成一段摘要**：一整段文字是黑盒。模型可能漏掉或编造，用户看不到也改不了，矛盾的话被揉在一起，很难测试。
- **压成一条条清单**（Meri 选这个）：每条都带用户原话，代码能校验原话是否真的出现过；用户能删能改；新的话可以取代旧的；每一条都能单独测试。

Mastra 自带两种长期记忆：working memory（Agent 自己维护的用户档案）和 semantic recall（用向量检索翻历史）。Meri 不用 working memory：它由 Agent 直接改写，没法插入"校验原话"这一步；而且记忆是用户看得见、能改的产品数据，应该存在 Meri 自己的数据库里。Planner 改记忆，通过我们自己写的工具。

## 第 5 课：交接（handoff）与 context engineering

固定流程和 Agent 之间怎么传上下文？不要把原始历史整个扔过去，而是在边界上**整理成一份交接包**。

Meri 的交接发生在点 Generate plan 时：
- TripState 快照：事实，以它为准；
- 从聊天一次性提取的记忆清单：偏好和约束，每条带原话；
- 今天的日期、语言。

之后计划页的对话由 Planner 处理，记忆也由 Planner 维护。

为什么这样做：
- 原始历史里有删掉的地点、改过口的话，Agent 自己分辨不清；
- 交接包短，每一轮都要发给模型，越短越快越便宜；
- 交接包每一项都能单独检查和测试。

决定模型看到什么、不看到什么，叫 **context engineering**。它对 Agent 表现的影响常常比改提示词还大。

## 第 6 课：工具就是我们写的函数

工具不是下载来的东西，而是**一个普通函数，加一份给模型看的说明书**：

```ts
createTool({
  id: "remember",
  description: "记下用户的一个偏好或约束，必须附上用户原话",     // 给模型看的说明书
  inputSchema: z.object({ text: z.string(), quote: z.string() }), // 模型必须按这个格式提参数
  execute: async ({ text, quote }) => {
    // 我们的代码：检查 quote 是否真的出现在用户消息里，通过了才写进数据库
  },
})
```

模型只能"请求"调用，做不做、怎么做由 `execute` 里的代码决定。Meri 现有的例子：[resolve-place.ts](../../src/agents/tools/resolve-place.ts)。

## 第 7 课：分区块计划和依赖关系

把计划拆成区块，每个区块写明它需要什么信息（由代码判断）：

| 区块 | 需要 |
| --- | --- |
| 示范一天 | 目的地 |
| 其余几天 | 天数 |
| 机票 / 高铁 | 出发地，交通方式不是自驾 |
| 天气、酒店价格 | 出发日期 |

用户补了一项信息，**只重算依赖它的区块**。比如填了出发地，只跑"怎么到那里"，Agent 只查机票和高铁。这和电子表格改一个格子、只重算相关公式是同一个思路，叫**依赖图上的增量重算**。

好处：每次重算都小，所以快、便宜、更不容易错；页面上一块块解锁、填充，也正好适合做动态效果。

## 第 8 课：真实进度，而不是假进度条

Agent 跑一次要十几秒到一分钟。常见的偷懒做法是按时间涨的假进度条，问题是它和实际不符：卡住时还在涨，快完成时又停在 99%。

真实进度的做法：
- 工作流每完成一步（核实地点、查路线、排好第一天），服务器就推一个事件给浏览器；
- 浏览器收到事件，进度条走一格，并显示这一步做了什么；
- 用流式传输（Meri 的照片已经这样做：服务器一条条推 NDJSON，浏览器边收边显示）。

这样进度条本身就是 Agent 在做什么的可视化，也是 human-in-the-loop 的基础：如果有一步需要用户回答，进度就停在那一格，等用户回答再继续。

## 面试问答

### 为什么不用现成的 memory，要自己写？

> 这是一个"自己做还是用现成的"的决定，我是从需求倒推的。
>
> 现成的记忆方案，基本做法都是让模型自己决定记住什么、怎么改写，记忆是给模型看的内部状态。但在 Meri 里，记忆直接影响生成的旅行计划，比如"不吃辣""一天最多走 15 公里""父亲膝盖不好"。所以我们对它有三个要求，现成方案都满足不了：
>
> 1. **可验证。** 每条记忆必须附上用户的原话，写入前由代码检查这句原话真的出现在用户的消息里，对不上就拒绝写入。现成方案由模型直接写入，没有地方插入这一步校验，模型把"可以吃一点辣"记成"不吃辣"，系统发现不了。我们在其他地方已经实测过这类问题：模型声称两个地点都核实过了，其实有一个没核实成功。
> 2. **用户看得见、改得了。** 记忆是产品的一部分，不只是模型的内部状态。用户在计划页能看到 Meri 记住的每一条，能删、能改、能否定。用户画像应该能被生成、被修改、被否定，而不是一个用户看不到的黑盒。
> 3. **取代关系清楚。** 用户先说"不吃辣"，后来说"其实微辣可以"，新的一条取代旧的一条，旧的一条保留并标为已取代，而不是把两句话揉成一段新的摘要。这样每一次变化都能追溯，也能单独测试。
>
> 自己写的部分其实很少：一张表、两个工具（`remember`、`forget`）、一个校验函数。存储、工具调用、Agent 循环这些通用能力仍然用框架的；我们只写业务规则，而这部分本来就应该由自己掌握。另外，记忆存在自己的数据库里，评估可以直接读取，以后换框架也不用迁移数据。
>
> 如果要进一步证明这个决定，我会在评估里把现成方案当对照组：用同一批对话，比较两边的提取准确率和编造率，用数据说话。

### 一个 Agent 跑多个小任务，还是多个 Agent？

Meri 用同一个 Planner 跑多个小范围的区块任务（示范一天、其余几天、怎么到那里……），每个任务输入不同、预算不同。多个 Agent 互相配合（multi-agent）要处理分工、通信和冲突，更难测试；只有一个 Agent 的工具和指令多到互相干扰时才值得拆。
