# Meri Generate Plan 实施交接

2026-11-16 · 设计和待办（1.2017 节奏方向由代码执行）。真实按钮已交接旅程快照和偏好到计划页，计划页通过工作流生成全部日程并实时显示进度。`/plan-preview` 使用独立的示例数据。流程顺序和首版范围以本文为准，其他产品决定见 [Planner 规划笔记](README.md)。

## 交接与锁定

- **单向流程。** 点 Generate plan 后进入计划页，不再回到 Workspace，计划不会因为 Workspace 改动而过期。
- **锁定。** Workspace 已填的事实（目的地、出发地、日期、天数、交通方式）交接后锁定。空着的事实可以在计划页补一次，用户确认后同样锁定，因为行程依赖它们。
- **偏好。** 交接时读取整段 Workspace 对话，上限约 30 轮并设 token 上限（多数旅程约 10 轮就定下来）。每条偏好带一个类型标签：节奏、步行上限、同行人、预算、饮食、兴趣、明确不要。标签给用户看，背后的原话和对话给模型用；代码用类型筛选候选，后续 Jev 也按类型打分。

## 生成流程

1. **读取 TripState 快照。** 已选省、市和景点决定规划范围。Workspace 跨省合计最多新增至 10 个城市／自治州，空省和景点不占城市名额。聊天只用于提取偏好。新增候选属于本次计划，用户已删除的地点不能从历史对话恢复为已选地点。
2. **按城市做第一轮调研。** Kimi 先按天数提名城市代表景点（每天约 3 个，每城 4–12 个），提名只是提案；代码把提名和点名景点每 3 个一组用 Kimi `search_pro` 并行核实，Agent 可再补查一次，没有原文出处的提名不成卡（1.2004 起，取代先搜城市候选）。已确认天数时覆盖最多 10 个已选城市，每批并行两城，每城最多 5 次查询。查不到的点名景点仍保留，并标明未知。以后由景点库取代提名这一步。
3. **先分天。** 多城市且总天数已确认时，Plan Agent 看各城候选摘要、偏好和已知转场时间，提出城市顺序、各天所在城市和停留晚数，决定哪座城多玩、哪座少玩。代码只核对天数、已选城市和用户确认的顺序，不替模型分配。偏好不足以做出取舍时，Plan Agent 可以暂停生成，在计划页弹出交互框问用户（例如偏好烟火气还是山水），最多问 1–2 次；回答存为一条带类型的偏好并锁定，工作流从暂停处继续。单城市由代码直接分天。没有确认总天数时，只调研第一个已选城市、生成示范第一天；总天数留空，「剩下的几天」等用户输入或确认后再解锁。
4. **按天筛选和排程。** 代码按所在城市、开放窗口和已知限制筛候选。周一闭馆只排除周一。普通降雨等体验因素可以交给 Jev，按当天条件和用户偏好为可选景点打分。用户指定的景点保留，排不进去就显示冲突。由同一个 Plan Agent 填充每天的景点和建议时间。工作流在两个阶段之间传递结构化数据，分天和日程分别校验。日期未知时用相对天序，天气和日期相关的开放状态标为待核实。
5. **精查草稿。** 核实拟排景点和少量备选在拟定日期的开放、预约和临时通知。首版由代码检查已知冲突，同一个 Plan Agent 指出需要补查的城市、日期和原因。Research 补足证据后，Plan Agent 只改受影响的日期。独立审核 Agent 留待对照测试。
6. **校验路线和结果。** 代码根据选点安排路线顺序，使用路线工具的结果核对车程、转场和开放窗口。缺少车程就标未知。检查候选范围、跨天重复和用户指定景点的覆盖。排不下时只重排受影响的天，预算耗尽则交付能用的部分并显示原因。
7. **审核兜底。** 基线跑通后加入审核 Agent，从旅行者角度检查整份计划，只退回问题或请调研刷新景点卡，不直接改计划。

## 计划页对话分流（设计）

生成真实行程后，计划页底部的修改对话框由 Jev（typesafe）判断消息交给 Kimi 还是交给 Agent：询问已有计划、调整现有行程、需要补查资料，还是需要澄清。问答交给 Kimi 读取计划和已有证据。调整行程由代码校验范围后调用 Plan Agent，缺事实才触发定向 Research。消息想改锁定的事实（例如换目的地、改天数）时交给 Kimi 回复，不用「不能修改」这类拒绝话术，而是说明现在能怎么做。置信度低时先澄清或交给 Kimi 理解。首版对照中文样例测试分流效果。

## 数据交接

| 数据 | 最小内容 |
| --- | --- |
| 景点卡 `SpotCard` | 景点 ID、城市、名称、用户是否点名、开放与预约、室内外与步行强度、建议停留时间。事实附来源和查询时间，未知字段显式表示。 |
| 计划草稿 `PlanDraft` | 日期或相对天序、城市、景点 ID、建议时段、路线或车程、冲突和未知项。模型以景点 ID 引用候选，代码补入路线和核验结果。 |

## 实施顺序

- [x] **接通 Workspace 交接。** 点击后服务端读取保存的状态和用户原话，交给真实计划页。同一标签页刷新复用快照。
- [x] **接通第一轮调研。** 验证脚本读取 PlanHandoff JSON，通过 Kimi 搜索按城市产出带原文出处的景点卡。只有省份时报告待确定的省范围。按钮仍只执行交接。
- [x] **单城端到端。** 1.2003 核心：`PlanDraft`、代码分天、Plan Agent 选点和时间锚点、代码校验和一次重试；1.2004 改为 Kimi 提名加搜索核实；1.2005 计划页通过 `POST /api/trips/[id]/plan-draft` 显示每天的景点、时段、时间锚点、出处和冲突，结果缓存在当前标签页。定义 `PlanDraft`。用测试景点卡跑单城示范第一天和单城明确天数，Plan Agent 选点和建议时段，代码校验天数、点名景点和跨天重复，不通过时把原因交回模型重试一次。核心放在 `src/agents/planner/`，外部接口放在 `src/platform/`。城市、天数和候选都通过参数传入。先用脚本和测试跑通，再把日程接到页面。
- [x] **偏好标签。** 1.2007：交接时读整段对话（30 条、12,000 字符）提取偏好，每条有原话（给 AI）、短标签（给用户）和不显示的类型（给代码）；存进 `trip_preferences` 表，计划页可增删；体力和同行人类偏好让每天最多 3 个景点。
- [x] **多城分天。** 1.2009：Plan Agent 先为每个行程（单城也是）规划路线：城市顺序、每城天数和理由、每天的重点区县和主题；天数少于城市时可放弃城市并写原因。代码校验覆盖、天数和区县，不通过重试一次再按添加顺序兜底。转场日少排 1 个景点并标车程待核实。天数不够时的「生成中提问加天数」留给下一步。
- [x] **工作流和实时进度。** 1.2010：生成改成 Mastra 工作流（读取范围 → 各城调研，两城并行 → 天地图定位 → 路线 → 逐城选点 → 配图 → 保存），子 Agent 都是 `src/agents/planner/` 里可单独调用的函数（Plan Agent 拆成 `plan-route.ts` 和 `plan-days.ts`），工作流在 `src/agents/workflows/plan-generation.ts` 只做编排。进度事件格式在 `src/domain/plan/plan-progress.ts`，用 SSE 推给计划页的实时活动流，路线和每天的卡片逐块出现；运行记录、事件和计划版本存进 `plan_runs`、`plan_run_events`、`plan_versions`。Mastra 状态暂存内存，服务器重启的运行标为中断，不自动续跑。实测丽江大理 5 天 40–43 秒。
- [x] **生成中提问。** 1.2011：多城全程时，Plan Agent 规划路线前可以问一个带选项的问题（加「你来定」），工作流用 Mastra `suspend` 暂停，快照存进 Neon 的 `mastra` schema（`@mastra/pg` 1.29.0，配 core 1.74.0）。回答存成 `source = question` 的偏好，从快照恢复，只重跑路线及之后的步骤。服务器重启后照样能回答、接着跑（已实测）。每次运行最多问 1 次；不问「加天数」（会改锁定的天数）。
- [x] **路线质量（1.2012）。** 天数够时 Kimi 不能自己放弃城市，觉得赶就提问（选项写明放弃哪座城，不提议加天数）；用户点名的区县名（如大理市）当作重点区域，不当作一站。
- [x] **验证阶段与第二轮精查（1.2013）。** 按天选景点之后加验证阶段：固定搜索收集开放、闭馆、预约事实，Kimi 拆成规则附原文，代码核对并按日期判断；关闭的先由代码换日，改不了的交 Plan Agent 只重排受影响的天，Mastra `dountil` 循环最多 2 轮，仍关闭的标冲突。天气、车程以后作为同一阶段的检查项加入；审核 Agent 留在这一阶段，等评测证明有用再做。
- [x] **评测集（1.2014）。** `evals/plan/cases/` 10 个典型旅程，`scripts/eval-plan.ts` 用真实工作流逐个跑，记录时长、token（调研的 token 起计入）、搜索、天地图查询、重试、覆盖、检查结果、预约、冲突和修复轮数，代码判定每个用例的断言，结果按版本存进 `evals/plan/results/`。天地图定位停下即终止整批。后面的审核 Agent、Kimi 与 Jev 对比都用这套数据比较。
- [x] **调研的城市判断（1.2015）。** 评测发现迪庆从不出卡：Kimi 把城市填成区县（香格里拉），代码只认迪庆。改为位置引用这一句写到这座城市（全名或「迪庆」这样的词干）就算在城里；原规则保留。复跑用例 3、4，迪庆每次有卡，用例 4 三城 3 次都保留。
- [x] **谁决定提问（1.2016）。** 用例 4 偏好已说想多看却仍问「是否保留三城」：提示词改为偏好说明了就不问。随后用例 3（2 天 3 城、无偏好）变成从不提问：这种情况代码自己能判断，改由代码要求——天数少于城市且没有兴趣或节奏偏好时，没带问题的路线退回再答一次。重复放弃同一城市的选项只留第一个。复跑：用例 3 问 3/3，用例 4 不问 3/3、三城都保留，用例 11 问 2/3。下一步 1.2017：偏好带隐藏的节奏方向（紧凑／轻松），由代码判断。
- [x] **隐藏的节奏方向（1.2017）。** 节奏类偏好多一个不显示的 `pace`（packed 想多看、能接受紧凑／relaxed 想轻松／空），提取、计划页手写、回答提问时由模型判断一次，存进 `trip_preferences.pace`（迁移 0013）。代码据此决定：每城都排得下且 packed → 不问是否放弃城市；relaxed → 每天最多 3 个景点。复跑：用例 4 不问 3/3，用例 3 问 3/3，用例 2、11 每天不超过 3 个。以后 Jev 打分也读这个字段。
- [ ] **接审核。** 基于拟定日期核实草稿和备选，再加审核 Agent。比较候选覆盖、行程可行性、搜索次数、耗时和 token。先建立 Plan Agent 选点基线，再对照 Jev 的中文评分效果。
- [ ] **分批接提供方和产品入口。** 按需要接天气、机票、酒店和高铁。接入真实生成时确定运行接口、计划存储、进度及失败恢复。
- [ ] **最后接天地图。** 1.2006 已接景点定位：有出处的景点查一次天地图，记区县，供同日分组和页面标记；失败即停、不重试，结果缓存。剩下：地点坐标、景点间车程、城市转场和浏览器地图。开发机曾被天地图防火墙拒绝（418），2026-11-12 起已在白名单内、可直接调用；实测仍先只发一个请求，失败就停。适配器按示例响应写测试，验证脚本输出脱敏。天地图核实只降低可信度、不当硬门槛：查不到的景点保留并标「位置未核实」，坐标用于同日分组和车程。
- [ ] **部署和评测。** 部署到美国 VPS，上线前实测天地图、Kimi 和 Neon 的可达性与延迟。项目完成后建立评测集，对比 Kimi 与 Jev、单 Agent 与多 Agent。

## 第一轮验收

| 输入 | 应看到的结果 |
| --- | --- |
| 只选一个城市，未确认天数 | 示范第一天可生成，后续日程锁住。 |
| 丽江、大理共五天，提供测试转场时间 | 覆盖两座城市，总天数对得上，转场计入时间，无跨天重复景点。城市如何分天由输入决定。 |
| 用户点名的景点当天闭馆 | 能换日就换日，排不进去就说明冲突。其余可用结果照常返回。 |

待定事项包括只有省份时是否要求先选城市（当前建议）、首批候选的发现查询，以及真实供应商的返回质量和预算上限。
