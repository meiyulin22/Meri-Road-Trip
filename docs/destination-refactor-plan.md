## 1. 用户目标与已确认决定

- 在 Claude 留下的未提交改动上继续完成 destination 重构，不重置、覆盖或丢弃这些改动。
- 已添加目的地按「省 → 市／自治州」展示，支持持续追加、删除。
- 聊天中找到地点并通过高德核验后，显示添加按钮；用户点击后才进入正式旅程。
- 保留具体景点意图，例如「梅里雪山」，作为所属市／自治州下面的 `spots`，供未来 Generate Plan 使用。
- 删除城市时同时删除它的所有 spots；单独删除 spot 不删除城市。
- **用户已确认：删掉省内最后一个城市后仍保留该省，表示还想去这个省。** 空省显示「尚未选择城市」。
- spots 表示「用户想去的具体地点」，不自动升级为必须完成的行程约束，也不表示已验证开放、安全或可达。
- 本轮不实现 Generate Plan、Research Agent 或通用 workflow 框架。
- 数据处理尚待用户回复；在明确允许清理前，按保留现有旅程与历史消息设计，不执行清库。

## 3. 审查发现

### A. 重构尚未接通，当前不可交付

`npx tsc --noEmit --pretty false` 失败：291 条错误，涉及 59 个路径，其中包含一个旧 `.next` 路由类型引用；其余大量错误来自真实源码和测试的新旧契约不一致。

`npm test` 也失败，包含找不到已删除模块、旧数据形状被拒绝、旧消息 presentation 不匹配等。

聊天 API、Journey 创建、规划准备检查、ConversationPanel 仍引用已删除文件；推荐生成器、选择 API、位置编辑器、聊天历史上下文、摘要投影、脚本和测试还在读旧字段。不能仅靠修正类型断言解决。

### B. 唯一解析结果会直接修改目的地

`apply-destination-edit.ts` 将 resolved picks 直接合并到正式 destination，set 时还会清空旧目的地作为基底。这与本轮「核验后显示添加按钮」要求不符。

修正：把提议／核验和提交分开。自然语言 add/set 先产生持久化的已核验候选；正式状态只由显式选择提交改变。remove 可以作为明确用户指令执行，但目标必须唯一。

### C. 不同 POI 被按同一城市折叠

`resolve-destination-place.ts` 的 `distinctPicks()` 只用省、市去重，多条 POI 在同一城市会被折叠，甚至从 ambiguous 变成 resolved。`apply-destination-edit.ts` 的候选生成也按省、市去重。两个不同景点不能因为同属一市就被认定为同一个地点。

修正：省市归组与 POI 身份去重分开。只按已核实的相同身份去重；多义名称的候选必须保留供用户选择。`resolution.options[0]` 也不能作为消歧的默认答案。

### D. 旧数据兼容已被移除

新 `validateDestinationField()` 拒绝旧 `value`、旧状态以及字符串 places；新 `validatePresentation()` 只读新 presentation。Postgres 仓库直接用这些校验器读取 JSON，已有 Journey 或聊天可能因此打不开。

在数据政策确认前，必须安排显式迁移／读取适配。不能把旧景点名称一律当作市，也不能把未知数据丢掉或伪称已经高德核验。

### E. 删除使用前缀匹配并取第一个结果

`findInDestination()` 的 `startsWith()` 在名称相似时会删除错误目标。

修正：UI 删除传稳定 ID；聊天删除先匹配当前状态里的候选，只有唯一匹配才执行，歧义时询问目标。不要从历史聊天推断已经被删除的地点仍属于当前偏好。

### F. 地点身份与来源信息会丢失

新 DestinationChoice 只有名称、province、spot 和临时／provider id；最终 spots 是字符串。高德 canonical name、POI 身份、坐标未进入最终 spot 数据。

建议为 spots 保存用户名称和最小核验身份，使以后规划能准确重新查询，也能区分同名地点。城市坐标不能错误地拿景点坐标充当。

### G. 省级准备度规则被一并改变

Claude 新规则将任意非空目的地认定为可规划。它是独立的产品行为变更，不是省市列表重构的必然结果。

本计划默认保留原「至少确定具体城市／地点才通过准备检查」体验。保留空省不等于宣称规划已经准备好。若用户希望仅选省即可规划，再明确修改这一条。

### H. Prompt、Schema 与文档需要同步

解释器 schema 已改为 destinationEdit，但 prompt 仍要求旧 intent、destinationDisambiguation 和 destination.value，模型会收到矛盾要求。首页草稿入口也有同类问题。

PROJECT / ARCHITECTURE 对推荐流水线的描述还包含当前工作流代码未执行的访问检查、图片补全等内容；实施时修正与本次目的地路径直接相关的段落，以运行代码为准。

## 4. 推荐界面方案

沿用现有米白背景、绿色强调、轻边框和圆角。新增独立 DestinationEditor；LocationEditor 留给出发地，避免两种完全不同的数据操作挤在一个组件里。

已添加目的地使用紧凑分组卡：

```text
目的地                            ＋ 添加地点

云南省                                  ×
  迪庆藏族自治州                        ×
    想去：梅里雪山 ×

广东省                                  ×
  潮州市                                ×
  汕头市                                ×

福建省                                  ×
  尚未选择城市
```

- 主层级到市／自治州，spot 是次级小标签，不变成与城市并列的目的地。
- 空省可继续通过统一搜索添加城市，默认带该省范围。
- 删除城市连带删除 spot，保留省；删除省移除所有子项。
- 显示明确的行内保存状态与失败信息；失败恢复原值。可采用乐观更新，但必须有回滚，不能把网络失败表现成已保存。
- 不为普通删除增加确认弹窗。提供短暂撤销提示；撤销是受版本检查保护的局部恢复，不能用旧整个 TripState 覆盖后续添加。
- 长自治州名换行；小屏按钮保持可点击尺寸；操作支持键盘和可读的无障碍标签。

聊天中的候选样式：

```text
梅里雪山
云南省 · 迪庆藏族自治州
会保留为这个城市下的想去景点          ＋ 添加
```

- 高德成功核验且身份清楚：添加 → 添加中 → 已添加。
- 城市已添加但该 spot 尚未添加：仍可添加 spot，不因城市存在而禁用。
- 潮汕等区域：按省归组城市，每行能添加；保留「添加所选」批量入口，兼顾上一版多选操作。
- 同名地点歧义：显示地区／地址区分，用户选一个解释后再提交；不能把一个歧义表达的所有解释默认多选加入。
- 明确「改去」：候选先暂选，再以「替换为所选目的地」提交一次。不能逐行 replace 导致后点的城市抹掉前一个。
- 核验无结果／查询失败：不给可用的添加按钮，给可重试说明。
- 已添加状态由当前结构化 destination 计算，不再用全局 `destination.state === known` 禁用所有卡片。

## 5. 数据与职责建议

保留 Claude 的单一结构化事实来源：正式 destination 只保存已确认的省市和其 spots；展示字符串、标题、计数均派生，不重新存一份 value。

建议结构草图，实际 TypeScript 类型在实施第一步定稿：

```ts
type DestinationSpot = {
  id: string;
  name: string; // 用户要去的名称，例如「梅里雪山」
  location: {
    provider: "amap";
    providerId: string;
    name: string; // 高德规范名称
    longitude: number;
    latitude: number;
    coordinateSystem: "GCJ-02";
  };
};

type DestinationPlace = {
  id: string;
  name: string; // 市、自治州等地级区域
  spots: readonly DestinationSpot[];
};

type DestinationArea = {
  id: string;
  province: string;
  places: readonly DestinationPlace[];
};
```

- 省市 ID 是应用内稳定身份，创建后保持不变；服务端用高德规范行政名称归组，不信任模型编造身份。不为本轮新增通用地理实体库。
- spot 用 providerId 判断相同 POI，name 保留用户提及方式。普通推荐市不自动附带模型随口举例的景点。
- 地点可能跨行政区或高德无法给出可靠父级时保留未确认候选，询问用户；不硬编码「梅里雪山属于某省」等映射。
- 不用字符串前缀、字面相似或同市关系假装 POI 已经消歧。匹配别名需要有证据，否则保留多个选项。
- `DestinationPick` 改为 province / city / spot 的明确联合类型，避免 `place: null` 同时 `spot` 非空这样的无效组合。
- pending 候选存在持久化助手消息中；不塞入正式 areas。用户未点击时不能当作已选偏好送入未来规划。
- spots 是当前旅程的意图。删除城市后，当前状态及给未来规划的上下文不再包含其 spots；历史聊天作为历史记录保留，不据此自动恢复已删除意图。

只保留几层明确职责：

1. **LLM 解释**：给出 add/set/remove 和用户原话中的地点；给出推荐意图；不生成高德身份、不写状态。
2. **解析服务**：查高德，返回核验候选、歧义、无结果或 provider_error；不提交目的地。
3. **领域纯函数**：添加、替换、删除、去重、格式化；不调用网络或数据库。
4. **应用服务**：校验所属 Journey、持久化候选、处理显式选择和状态提交；统一供首页、聊天与编辑器使用。
5. **UI**：渲染省市、spots 和按钮状态；提交候选 ID／删除对象 ID，不自行拼权威地名。

推荐工作流生成的名称也要走相同高德验证边界。前端收到 `verified` 字段不构成授权证明；提交时服务端必须从自己持久化的 offer 或重新核验结果中取得候选。

## 6. 提交、重试和旧卡片

- 新选择只提交 messageId／offerId 与 choiceId，服务端验证属于当前用户和 Journey。
- 添加操作基于服务端最新状态合并；同一个景点重复提交不重复添加。
- 替换操作携带出卡时的目的地版本；旅程已变化则提示重新确认，禁止旧替换卡覆盖新选择。
- 删除按稳定 ID 定位。并发修改用事务或版本检查防止读旧状态后整段覆盖；只处理 destination 所需的并发边界，不扩展成通用事件系统。
- 状态成功但后续文案失败时，仍返回真实已保存状态；再次请求可恢复确认，不重复写入。
- 保存后重新打开 Journey，卡片、所选省市与 spots 都与持久化状态一致。
- 旧消息格式通过只读适配继续展示；没有核验身份的历史候选重新验证后才允许添加。不能因为旧卡没有新字段就让整个聊天加载失败。

## 8. 验收场景

1. 输入「我想去梅里雪山」：高德核验 → 卡上保留梅里雪山和行政归属 → 点击添加 → 右侧显示省、市以及想去景点；点击前正式 destination 不变。
2. 同市再加一个不同景点：同一个市下新增 spot；原景点不丢失。重复添加同一 POI 不重复。
3. 删除该市：全部 spots 从正式状态删除，省保留为空；刷新、重开、后续聊天均不自动恢复它们。
4. 先选浙江、福建，再说还想去潮汕：核验后的广东城市可继续添加，已有省市和 spots 保留。
5. 「改去潮汕」：选择多个市并一次替换；未提交、失败或旧卡过期都不清空当前旅程。
6. 输入同名或同市多个 POI：用户能区分候选，不自动选第一个、不把多个真实 POI 合成同一个。
7. 未找到、缺父级、高德超时：不显示可成功添加的假选项，不改正式状态，可以重试。
8. 连续点击、网络重试、多标签页操作、状态已存但回复失败：无重复地点，无旧状态覆盖，无虚假成功。
9. 城市存在但新 spot 尚未存在：按钮可添加 spot；省市存在不会锁死整个候选区。
10. 历史旅程与卡片按最终数据政策可读；当前新选择刷新后仍可恢复。首页创建与 Workspace 连续对话行为一致。

## 9. 交接给 Sol

实施范围限于本计划的目的地重构及必要调用方，不扩展到 Research Agent 或未来规划执行。可以重整 destination 模块，但不要同时重写无关日期、交通、认证等模块。

先完成一条「聊天解析 → 高德候选 → 点击添加 → 省市与 spot 存储 → 右侧展示」纵向链路，再补替换、删除、推荐与旧数据边界。每阶段记录真实检查结果，最终交付说明仍存在的限制。
